SECTION 1: PROJECT OVERVIEW
============================================================

PROJECT DESCRIPTION:

Develop a web-based Pickleball Match Queuing System designed
to manage open-play pickleball sessions.

The system will allow an organizer to register players,
configure courts, manage player queues, generate matches
based on skill levels, record match results, and maintain
individual player standings.

The system will have two primary interfaces:

1. ORGANIZER DASHBOARD
   - Used by the event organizer.
   - Allows management of players, courts, matches,
     queues, scores, and standings.

2. PUBLIC DISPLAY
   - Designed for a TV or monitor.
   - Displays current matches, court assignments,
     waiting players, completed games, and standings.
   - Read-only interface.
   - Automatically updates when the organizer changes
     information.

PRIMARY OBJECTIVE:

Build a functional and expandable application that can
manage actual open-play pickleball sessions.

DEVELOPMENT PRIORITY:

1. Functional correctness.
2. Fair and reliable matchmaking.
3. Accurate player and match records.
4. Maintainable software architecture.
5. User interface and user experience.
6. Future scalability and additional features.

SECTION 3: SYSTEM ARCHITECTURE
============================================================

Follow a layered architecture.

1. CONTROLLER LAYER
   - Receives HTTP requests.
   - Validates incoming requests.
   - Calls the appropriate service.
   - Returns webpages or response data.

2. SERVICE LAYER
   - Contains application business logic.
   - Handles player management.
   - Handles session management.
   - Handles court management.
   - Handles matchmaking.
   - Handles match results and standings.

3. REPOSITORY LAYER
   - Handles database access.
   - Uses Spring Data JPA.

4. ENTITY LAYER
   - Represents database entities.
   - Defines relationships between entities.

5. DTO LAYER
   - Transfers data between application layers
     and the frontend.
   - Avoid exposing database entities directly
     through external interfaces.

6. CONFIGURATION LAYER
   - Contains application configuration.
   - Handles security and other shared settings.

ARCHITECTURAL RULES:

- Controllers must not contain matchmaking algorithms.
- Controllers must not directly execute complex database
  operations.
- Business logic belongs in service classes.
- Database operations belong in repositories.
- Matchmaking must be independently testable.
- Use transactions for operations that must succeed
  or fail as a complete unit.
- Avoid tightly coupling the frontend and backend.

SECTION 4: CORE SYSTEM REQUIREMENTS
============================================================

FEATURE 1: PLAYER MANAGEMENT

The system must allow the organizer to:

- Register players.
- Edit player information.
- Remove or deactivate players.
- Assign skill ratings.
- View registered players.
- Enable or disable player participation.

PLAYER ATTRIBUTES:

- Player ID.
- Player name.
- Skill rating (1-10).
- Active status.
- Registration date.

SKILL RATING SCALE:

1 = Beginner.
10 = Highly skilled.

Skill ratings will initially be assigned manually.

FEATURE 2: SESSION MANAGEMENT

The system must support open-play sessions.

The organizer must be able to:

- Create a session.
- Name a session.
- Start and end a session.
- Register participating players.
- Track player attendance.
- View the current session.
- Preserve historical sessions.

A player must be reusable across multiple sessions.

FEATURE 3: COURT MANAGEMENT

The organizer must be able to:

- Configure the number of courts.
- Assign names or numbers to courts.
- Enable or disable courts.
- View available courts.
- View occupied courts.
- Assign matches to available courts.

A court must not have multiple simultaneous active
matches.

FEATURE 4: PLAYER QUEUE MANAGEMENT

The system must:

- Maintain a list of players waiting to play.
- Track players currently playing.
- Prevent players from being assigned to multiple
  simultaneous matches.
- Support adding and removing players from the queue.
- Track player participation.
- Support fair rotation between players.

FEATURE 5: MATCHMAKING

The system must:

- Generate matches automatically.
- Select four players per doubles match.
- Balance teams based on skill ratings.
- Randomize player pairings and opponents.
- Avoid repeatedly assigning the same partners.
- Avoid excessive opponent repetition.
- Consider previous match participation.
- Allow manual match modifications.
- Allow the organizer to approve generated matches.

MATCHMAKING PRIORITIES:

1. Prevent duplicate player assignments.
2. Distribute playing opportunities fairly.
3. Balance combined team skill.
4. Avoid repeating partners.
5. Avoid excessive opponent repetition.
6. Randomize equally suitable match configurations.

The algorithm must prioritize fairness and competitive
balance rather than unrestricted randomization.

FEATURE 6: MATCH MANAGEMENT

The system must:

- Generate matches.
- Assign matches to courts.
- Display assigned players.
- Track match status.
- Allow matches to begin.
- Allow matches to be completed.
- Support manual match cancellation.
- Preserve match history.

Suggested match statuses:

- PENDING.
- CONFIRMED.
- IN_PROGRESS.
- COMPLETED.
- CANCELLED.

FEATURE 7: SCORE MANAGEMENT

The organizer must be able to:

- Enter the final score.
- Identify the winning team.
- Complete a match.
- Correct incorrectly entered results through an
  explicit correction process.

Completed matches must update player standings.

FEATURE 8: STANDINGS

The system must track:

- Total matches played.
- Wins.
- Losses.
- Win percentage.

Standings must be calculated using completed match
results as the source of truth.

Avoid storing independently maintained win/loss totals
as the only source of truth.

FEATURE 9: PUBLIC DISPLAY

The public display must:

- Show active matches.
- Show court assignments.
- Show player names.
- Show waiting players.
- Show recently completed matches.
- Show player standings.
- Automatically receive updates through SSE.

The public display must be read-only.

It must not expose organizer controls.

SECTION 5: DATABASE DESIGN
============================================================

INITIAL CORE ENTITIES:

1. PLAYER

Purpose:
Stores registered player information.

Suggested attributes:
- player_id (Primary Key).
- player_name.
- skill_rating.
- is_active.
- created_at.

2. SESSION

Purpose:
Represents an open-play event.

Suggested attributes:
- session_id (Primary Key).
- session_name.
- session_date.
- session_status.
- created_at.
- ended_at.

3. SESSION_PLAYER

Purpose:
Associates players with open-play sessions.

Suggested attributes:
- session_player_id (Primary Key).
- session_id (Foreign Key).
- player_id (Foreign Key).
- participation_status.
- queue_position.
- joined_at.

4. COURT

Purpose:
Stores court information.

Suggested attributes:
- court_id (Primary Key).
- court_name.
- is_active.

5. SESSION_COURT

Purpose:
Associates courts with specific sessions.

Suggested attributes:
- session_court_id (Primary Key).
- session_id (Foreign Key).
- court_id (Foreign Key).
- availability_status.

6. MATCH

Purpose:
Stores individual matches.

Suggested attributes:
- match_id (Primary Key).
- session_id (Foreign Key).
- court_id or session_court_id (Foreign Key).
- match_status.
- scheduled_at.
- started_at.
- completed_at.

7. MATCH_PLAYER

Purpose:
Associates four players with a match.

Suggested attributes:
- match_id (Foreign Key).
- player_id (Foreign Key).
- team_number.

8. MATCH_RESULT

Purpose:
Stores the final score.

Suggested attributes:
- match_id (Primary Key and Foreign Key).
- team_1_score.
- team_2_score.
- winning_team.
- completed_at.

DATABASE DESIGN RULES:

- Use appropriate primary and foreign keys.
- Enforce valid skill ratings (1-10).
- Prevent duplicate player assignments within a match.
- Prevent duplicate active court assignments.
- Define appropriate relationships.
- Use database transactions for critical operations.
- Use Flyway for database schema migrations.
- Do not rely on frontend validation alone.
- Consider database constraints for important
  business rules.

IMPORTANT:

The initial database structure may be adjusted during
implementation if a better design is identified.

Any significant database changes must be documented
and explained before implementation.

SECTION 7: TESTING REQUIREMENTS
============================================================

Testing must be performed throughout development.

UNIT TESTING:

Focus on individual business logic components.

Examples:
- Skill rating validation.
- Team balancing.
- Player selection.
- Duplicate assignment prevention.
- Standings calculations.
- Match status transitions.

INTEGRATION TESTING:

Verify that different application components work
together.

Examples:
- Player registration and database persistence.
- Session creation and player registration.
- Match generation and database persistence.
- Score entry and standings updates.
- Match completion and court availability.

EDGE CASE TESTING:

Consider the following situations:

- Only three players are waiting.
- Exactly four players are waiting.
- More players are waiting than available courts.
- Players have identical skill ratings.
- Players have significantly different skill ratings.
- All courts are occupied.
- A player becomes unavailable.
- A match is cancelled.
- An incorrect score is submitted.
- The same score is submitted twice.
- Two organizers attempt conflicting operations.

Matchmaking must never assign a player to two
simultaneous matches.

Testing should be expanded as new features are added.
